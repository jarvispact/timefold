JavaScript Performance Best Practices for ECS Libraries
Memory & Allocation

Avoid frequent allocations: Reuse objects/arrays instead of creating new ones; every allocation creates GC pressure
Use object pools: Pre-allocate objects and recycle them rather than repeatedly allocating/deallocating
Prefer SMIs (Small Integers): Keep integers in the 31-bit range (-2^30 to 2^30-1) - they're stored inline without heap allocation
Minimize HeapNumber allocations: Operations that keep values as SMIs avoid expensive HeapNumber allocations on each update
Use typed arrays: TypedArrays (Int32Array, Float64Array, etc.) provide better memory locality and avoid boxing/unboxing overhead
Batch allocations: Group related allocations together rather than spreading them throughout execution

Data Structure & Layout

Maximize data locality: Keep frequently accessed data together in memory (arrays > objects with many scattered properties)
Use array-of-structs or struct-of-arrays: Choose based on access patterns - SoA often better for ECS iteration
Minimize object property additions after creation: V8 creates new "hidden classes" when properties are added dynamically
Initialize objects consistently: Create objects with the same shape in the same order to share hidden classes
Avoid sparse arrays: Dense arrays are much faster than sparse ones
Keep arrays homogeneous: Arrays with consistent types optimize better than mixed-type arrays

Type Stability

Maintain consistent types: Changing variable types causes deoptimization and prevents optimizations
Avoid polymorphism: Monomorphic call sites (single target) optimize much better than polymorphic (multiple targets)
Be careful with number types: Mixing integers and floats forces float operations; keep numeric operations consistent
Stabilize object shapes early: Don't modify object structures after optimization has occurred

Function & Control Flow

Write predictable branches: The JIT optimizes based on feedback - stable branch behavior enables better code generation
Avoid megamorphic call sites: More than 4 different call targets at a site prevents inlining
Enable inlining: Small, frequently-called functions benefit greatly from inlining (generally < 600 bytes of bytecode)
Minimize deoptimization: Avoid code patterns that cause frequent optimization/deoptimization cycles
Use simple loops: Traditional for loops optimize better than complex iterators

Numeric Operations

Use integer operations when possible: Integer arithmetic is faster than floating-point
Apply bitwise operations for integers: Operations like |0 can ensure SMI representation
Avoid mixed arithmetic: Keep operations consistently integer or consistently float
Be aware of division: Division can produce floats even with integer inputs; consider alternatives
Use Math.imul for integer multiplication: For guaranteed 32-bit integer multiplication

Memory Access Patterns

Sequential access is fastest: Access array elements in order for best cache performance
Minimize pointer chasing: Deep object property chains hurt cache locality
Group hot data together: Keep frequently-accessed fields in the same object/array region
Separate hot and cold data: Don't mix frequently-accessed with rarely-accessed data

Context & Closures

Minimize closure allocations: Each closure creates a new context object
Be careful with variable capture: Captured variables in closures live on the heap
Use module-level constants: Prefer const at module level over repeated allocations
Leverage static roots: Core JavaScript objects (undefined, null, true, false) have compile-time constant addresses

Effect Management

Minimize side effects: Pure functions optimize better than functions with side effects
Make dependencies explicit: Clear data flow helps optimization
Avoid aliasing issues: Multiple references to same memory confuse the optimizer

ECS-Specific

Component storage: Use TypedArrays for component data with consistent types
Entity IDs: Use integers (ideally SMIs) for entity identifiers
System iteration: Iterate over packed arrays rather than sparse collections
Query results: Cache and reuse query results rather than recreating them
Avoid entity.component.property chains: Flatten access patterns for better cache locality
Batch similar operations: Process components of same type together for better cache usage

Measurement & Validation

Profile before optimizing: Use V8's profiling tools to find actual bottlenecks
Test with realistic workloads: Microbenchmarks can mislead; test at scale
Monitor deoptimizations: Use --trace-deopt to identify optimization failures
Check memory usage: Watch for unexpected allocations with heap snapshots

Compiler-Friendly Patterns

Prefer early returns: Helps the compiler understand control flow
Use strict equality (===): Faster than coercive equality (==)
Avoid arguments object: Use rest parameters (...args) instead
Minimize try-catch scope: Isolate try-catch to small regions; it inhibits optimization
Use const/let over var: Enables temporal dead zone elimination optimizations
